## 3. Work list (in order)

**1. (B1, MUST) The single-instance lock must never wedge.**
`acquire_instance_lock` (`src/leasegrid_sync/app.py`, around line 124) calls `lock.setStaleLockTime(0)`, and the lock is never unlocked. As a result, an empty lock file, a garbage lock file, or a lock written by another host (a copied or migrated home) gives "already running" with no window, forever.
Fix:
- Remove `setStaleLockTime(0)`, keeping Qt's default stale time (or set an explicit sane value and log the decision).
- Unlock and remove the lock on clean quit (`quit()` / `shutdown()`), and make sure the lock object stays referenced for the life of the app.
DoD, with tests that are real processes or real lock files, not mocks:
- (a) An empty lock file older than the stale time recovers: the app starts. Set the file mtime into the past with `os.utime`.
- (b) A garbage lock file, likewise.
- (c) A foreign-host lock (Qt lock format with another hostname and a PID), likewise.
- (d) A live first instance is still refused. Tester verified this after 35 s. A test that waits 35 s is too slow for CI, so prove "still refused while the holder is alive" with the shortest wait that is honest, and log the choice.
- (e) A **REAL two-app-process test where the app itself is the first instance.** Start process 1 through the app's real entry path (`leasegrid_sync.cli.main` or the function `main` uses to take the lock and build the window, offscreen, with a temp `LEASEGRID_SYNC_HOME` and no Tahoe start; see Tester's `live/harness_app.py`). Wait until it holds the lock, then start process 2 and assert it is refused ("already running", exit 0, no daemon). Then close process 1 cleanly and assert that the lock file is gone and that a third launch is accepted.
- **Mutation proof required:** delete the line that keeps the lock referenced (`_INSTANCE_LOCK = lock`) and test (e) must go RED. Put `setStaleLockTime(0)` back and (a)–(c) must go RED. Log both.

**2. (B2, MUST) Never restore the window off-screen.**
`_restore_window_geometry` (around line 2207) stores `_pending_geometry_pos`. `show()` (around line 2182) then calls `move()` to it, which undoes Qt's on-screen clamp after `restoreGeometry`. A saved y = -650 comes back at -650 with the title bar off-screen.
Fix: drop the pending move, or apply it only when the saved title-bar strip lies inside some screen's `availableGeometry()`. Otherwise keep Qt's clamped position.
DoD: in `tests/test_sync_window_geometry.py`, saved geometry with the top at y = -650 (and a case left of the screen) restores with the title bar inside `availableGeometry()`. A normal on-screen position still round-trips exactly. Mutation: put the unconditional `move()` back, and the off-screen test goes RED.
