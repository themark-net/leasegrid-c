## 3. Work list

**1. (N1 blocker) The "Another invite arrived. Use it?" question is a nested modal inside the socket slot.**
`_accept_handed_invite` calls `QMessageBox.exec_()` from `take()` (the QLocalSocket readyRead/disconnected slot in `_start_join_server`). Each different invite nests another event loop; the 8-socket cap doesn't bound it because the 2 s timer frees slots. After a burst the app ignores SIGTERM (alive 20–82 s later), and SIGTERM with questions open crashes (rc -6 `std::bad_alloc`, rc -11). See REVIEW N1, `hung_trace.txt`, `crash_trace.out`.
- Fix: in `take()`, extract the text and `drop(sock)` **before** any UI call; hand the text to the UI via `QTimer.singleShot(0, …)` (never from inside the socket slot).
- Replace `exec_()` with a non-blocking `QMessageBox` (`open()` / `show()` + `finished`/`buttonClicked` signal), parented to the window, objectName `handedInviteReplace`, default No (Esc = No).
- Keep **at most one** pending replacement: if the question is already open, just replace the stored pending text (latest wins); no second box. Yes → the field becomes the latest pending text; No → keep typed text; either way clear pending. If a new invite equals the current field, nothing to ask. Never log either invite.
- SIGTERM/SIGINT/SIGHUP with the question open must quit cleanly: rc 0, lock removed, daemons stopped (close/delete the box on quit; no nested loop remains so the existing wakeup-fd handler works).
- Tests (real process, offscreen, via a `_TEST_HOOKS` driver like the existing join tests):
  - flood: field prefilled with A, then ≥400 rapid send-close connections each with a *different* invite → app alive; exactly one `handedInviteReplace` box (use an existing test hook/dump, e.g. extend `LEASEGRID_TEST_INVITE_DUMP` to record the count of open replace boxes and the pending text — the dump must never contain anything but fake invites); then SIGTERM → exits rc 0 within 15 s, lock removed.
  - SIGTERM-with-dialog-open: sequence A, B, B, no-newline payload, sleep 2 (Tester's crashing sequence), then SIGTERM → rc 0 (not -6/-11), lock removed.
  - latest wins: A typed, B then C handed → one box; Yes → field is C; No → field stays A.
- RED base: the flood test fails on b267059 (app alive after TERM timeout, or >1 box) and/or SIGTERM test sees rc -6/-11. RED mutant: call `box.exec_()` again (or drop the "one pending" guard) → RED.

**2. (N2 blocker) `reap_child` leaves a TERM-ignoring grandchild when the leader obeys TERM.**
In `src/leasegrid_sync/backend.py`, after SIGTERM to the group, `proc.poll()` reaps the leader, so the SIGKILL to the group is skipped and the grandchild survives (real Tahoe behavior). Also when the leader exits on its own before quit. The docstring's zombie-leader claim is false.
- Fix (POSIX, when `os.waitid` exists): detect leader exit **without reaping** using `os.waitid(os.P_PID, pid, os.WEXITED | os.WNOWAIT | os.WNOHANG)` in a short poll loop up to the timeout. Sequence: SIGTERM the group → wait (WNOWAIT) up to `terminate_timeout` for the leader → a short grace for TERM-obeying members (≤0.5 s) → `killpg(SIGKILL)` while the (possibly zombie) leader still pins the pgid → then reap (`proc.wait`, so `proc.returncode` is set). If the leader is still alive after the timeout, SIGKILL the group, then reap.
- Leader exited on its own: audit every place that `poll()`s / `wait()`s a group-leader daemon (status checks, stop paths). Use a non-reaping "has exited" check (waitid WNOWAIT) there so the zombie keeps pinning the pgid until `reap_child` kills the group and reaps. If `reap_child` is entered with the leader already an unreaped zombie, still killpg the group, then reap. If the leader was already reaped elsewhere (returncode set), do **not** signal the pgid (keep the pid-reuse guard, `test_reaped_leader_does_not_signal_a_reused_pid` must stay green).
- `ChildProcessError`/`OSError` from waitid → treat as already reaped (no group signal). Windows path (CTRL_BREAK then `taskkill /T /F`) unchanged and working; guard with `hasattr(os, "waitid")`/`sys.platform`. macOS CI must pass (os.waitid exists there; if CI shows it misbehaves, fall back on darwin and document).
- Rewrite the docstring to describe what really happens.
- Tests (real processes, POSIX-only skip with reason on Windows): (a) leader obeys TERM, grandchild ignores TERM → after `reap_child` the grandchild is gone (adapt `live/pg/reap_obey.py`); (b) leader exited on its own (unreaped) with a TERM-ignoring grandchild → app-level stop (`ctl.stop()` or `reap_child`) leaves no grandchild; (c) existing pid-reuse test still green. Kill only PIDs the test recorded.
- RED base: test (a) fails on b267059 (grandchild SURVIVED). RED mutants: skip the post-exit group SIGKILL → RED; replace the WNOWAIT check with `proc.poll()` → RED. Note in the run log that Tester's R3 survivor ("always kill the group") is now intended behavior while the leader is unreaped, and the pid-reuse test guards the reaped case.
